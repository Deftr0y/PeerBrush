# Production composition and immutable publication (unreleased)

PB-154 now has a prepared final-byte composition and immutable GitHub transaction. It remains disabled. Current native signing and installed-acceptance producer work is incomplete; configuration or a supplied readiness report cannot make this source production-ready. No release, Store submission, website deployment, environment or credential change is performed by developing these scripts.

## Final inputs and trust boundaries

`scripts/final_release.py` consumes the existing six-record candidate: Windows/macOS/Linux portable archives, matching GPL source, final DEB and final signed DMG. It reruns the existing archive/source, DEB and DMG consumers, including the selected Mac qualification's actual cryptographic verification and exact successful-job service readback. Its bounded Linux installation receipt is checked through `production_readiness.assess_deb`; matching receipt bytes remain distinct from authenticating the native job. Originals, copied bytes, source/version and native trust snapshots are checked again after composition.

Windows direct input selects the exact source-derived unsigned MSIX, signed revision, independently selected framework media, public identity/family and versioned App Installer descriptor. The aggregate reconstructs source payloads and compares both package variants, framework identity and the exact shared descriptor serializer. It does not run Windows signature verification from Linux, accept a qualification JSON as native authority, or establish executable signing. The existing Windows-native `prepare_appinstaller.py` remains the native verifier/preparer; authenticating its producer and binding approved executable signing/runtime redistribution are still required source work. The serializer extraction preserves its literal ASCII/XML and no-update-configuration rules.

The new `final-release-inventory.json` embeds the inspected base inventory and exact final-file hashes/sizes. It binds all three direct distribution channels and their dependencies, plus explicitly disabled/unverified Store status. Output contains only the selected public packages, source, bounded public candidate sidecars, this manifest and checksums computed after all final bytes. Unsigned MSIX inputs, identity selections, Linux installation receipts, attestation/verifier/trusted-root inputs and logs stay outside public output. Candidate files and same-version manifests are immutable; an interrupted composition uses a new private output directory.

The CLI takes a SHA-256-selected JSON containing only the explicit commit/version, Mac trust selectors, Windows file/identity/URI selectors, approved public DEB maintainer and private Linux receipt selection. Paths/hashes are selectors, not claims that checks passed. Unknown fields/readiness reports reject. A successful current composition returns exit 2 and its explicit native/approval blockers. It cannot publish.

## Publication and interruption recovery

`scripts/publish_release.py` consumes an in-process result of actual composition, never a deserialized ready report. Its public entry verifies the candidate again and stops before obtaining credentials while any native gate remains. The prepared `production.yml` runs source/version and offline contract checks on main; optional protected preparation also requires a successful exact-source release-candidate predecessor. Its publication job is unconditionally disabled and requests no contents-write permission. The selected final-input bundle producer and authenticated installed producers still need implementation before enabling that path; ordinary candidate artifacts do not already contain those inputs.

The prepared transaction implementation checks exact main/tag/source, all stable-release versions, reviewed notes and the complete immutable file set. It creates one draft, verifies actual existing remote bytes before resuming it, uploads only missing exact files, and publishes only after complete local/remote reconciliation. It never deletes/replaces assets, rewrites tags, edits existing notes or retries a mutation with an uncertain result. A later invocation reads the actual draft/release first. Ambiguous create/upload/publish outcomes remain held until that reconciliation; already published releases receive readback only. Each transfer has bounded bytes, response time and fixed official API/storage hosts, and tokens never follow download redirects.

After a publish response, actual unauthenticated public downloads and the resolved tag must match every final file, source and checksum. Delayed visibility or a missing/wrong platform fails readback; it does not trigger another publish, a replacement or a ready website row. This confirms asset availability only. App Installer referenced media/feed operation, signatures, installed behavior and Store public packages have separate acceptance gates.

The website's existing preparer recognizes the final manifest, binds it to its independently selected base inventory and reruns exact public-byte readback. It retains existing archive/source/installer checks and distribution policy. Windows direct files are explicitly excluded from selectable downloads until their native producer and installed acceptance adapter exists. Mac/Linux candidate metadata cannot become native acceptance. With no eligible public platform, it produces an exclusion report and leaves the existing home/latest/history untouched. Eligible history continues through the existing renderer, which preserves prior notes, source pins and links. Website deployment still uses the separately reviewed `site-content`/Pages procedure and approval.

## Store state and remaining work

Store submission stays disabled: there is no approved durable private backend. The prepared status adapter reuses the existing read-only durable reconciler. Certification pending, rejected, failed, publishing and published are separate service states; even Published is not proof of public package availability. Unknown or ambiguous outcomes never cause submission or duplicate retries. No Store credentials, account identifiers or receipt contents enter final public files. Future stores require a specific reviewed channel/producer/availability adapter; unknown manifest channels reject.

PB-154 remains open. Required source/native work includes the Windows hardware/provider-backed executable and MSIX signing producer, authenticated final native handoffs/installed-evidence producers, real installation/upgrading/settings/file-open/interruption/unsaved-work coverage on each OS, final installer website/update-discovery adapters and approved feed/runtime media checks. Required external gates include approved publisher identities, signing/notarization access, runtime redistribution approval, protected preparation/publication configuration, Store durable storage and explicit release/Store/site authorization. No private key or credential belongs in the repository or selection JSON.

They have not yet run in combined QA. Synthetic signatures and fake native verifier/service results establish no operating-system trust or installed acceptance.
