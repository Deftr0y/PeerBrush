# Update discovery and restart protection (PB-147 development)

This is an unreleased discovery/safety slice. It checks actual official release metadata and protects a future installer restart. It does not download executable packages, install updates or restart PeerBrush. A published filename or checksum is never treated as a verified package signature or a ready-to-install update.

## Current behavior

File → Updates opens a compact panel with the current application version, installation owner, Stable/Preview channel, opt-in daily checks, Check now, actual request/read progress, release notes, errors and Later. Preferences use the existing guarded per-user profile or explicit instance-local workspace as `updates.json`, independently from artwork and document history. Automatic checks are off until enabled. The last attempt is retained across restarts to limit automatic checks to once per day. A failed check replaces any earlier success; offline or malformed responses never mean up to date. Background notices wait for idle native input and editors, including unfinished strokes and gestures; unsaved artwork alone does not delay a notice. Manual menu opening stays immediate. Closing the panel defers attention for the current check without closing projects, including when its response is still in flight.

`peerbrush updates check` performs the same real check without opening a document. `--preview` includes published prereleases. These command-line checks do not change preferences. They report metadata only.

The fixed request is the public GitHub releases collection for `Deftr0y/PeerBrush`, with at most 100 entries and 2 MiB. It uses the existing `ureq` client with TLS enabled, standard certificate/hostname validation and bundled Mozilla trust roots. HTTPS is required; redirects are disabled. Connections and reads have five-second limits and the request has a 25-second total limit. No API credentials or arbitrary endpoint override is accepted.

Discovery excludes drafts/unpublished entries, compares full SemVer precedence and separates stable from prerelease selection. A tag must parse as an exact semantic version, optionally prefixed by `v`. Returned release/asset URLs must be the exact canonical HTTPS paths for this repository and tag; credentials, query/fragment additions, other origins and path tricks are rejected. It bounds assets, filenames, advertised package sizes and displayed notes. Notes render as plain text, with an official release link for full details.

Only uploaded, nonempty packages matching the exact version and supported architecture are listed. Windows x64 and Linux x64 portable ZIPs, the corresponding Linux amd64 DEB and macOS arm64 ZIP/signed-DMG names are recognized. Candidate DMGs are excluded. Package names alone establish no signing status. If a newer release lacks the current platform/architecture, the panel states that its download is unavailable; it never substitutes an older platform package. The checker inspects the latest bounded collection, not an arbitrary `latest` redirect or an invented download path.

## Installation ownership

Windows reads package identity and native `Package.SignatureKind`: Store-signed installations always remain Microsoft Store-managed. For the supported non-Store `Developer` and `Enterprise` signature categories, a successful non-null [GetAppInstallerInfo](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.package.getappinstallerinfo) result identifies an App Installer association. This local query does not read or expose its potentially private URI, contact an update server, change installation settings or invoke deployment. Association alone establishes neither an approved PeerBrush direct-distribution identity nor configured automatic updates, available packages or verified future package signatures. The existing public release check and restart protections remain separate.

Missing/null, unavailable or failed association queries retain the conservative Windows-package/provider label. Unsigned, system and unrecognized signature categories also retain that label without querying an association; failed identity, package or signature queries remain unknown. A package identity alone never establishes Store origin. Microsoft's [`Developer` signature category](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.packagesignaturekind) describes a trusted certificate outside its Store/Enterprise/System categories; it does not mean a development build. The association API requires Windows 10 version 1809, below the current MSIX minimum build 19041, and uses the existing Windows bindings. Native installed Store/App Installer/other-package acceptance remains pending; synthetic classification and panel checks do not establish it.

For an installed Store-signed app, a separate **Check Microsoft Store** control now prepares a native read-only availability query. It starts on the actual eframe window thread, associates `StoreContext` with that window through `IInitializeWithWindow`, and polls `GetAppAndOptionalStorePackageUpdatesAsync` without waiting for completion on the UI thread. Public GitHub notes and the Stable/Preview preference remain independent; they never establish Store availability. Native queries are manual only. No download, installation, licensing purchase or restart API is invoked, and no package capabilities are added.

Only a result for the exact current package full name and family is accepted. Optional packages in another family do not establish an update for the main app. Microsoft's [Package property](https://learn.microsoft.com/en-us/uwp/api/windows.services.store.storepackageupdate.package) describes a package with an available update but does not specify whether its ID version is installed or offered. A different full name in the same family is therefore reported as unknown, rather than interpreted as no update or as a version to install. Duplicate or oversized results, failed identity/signature rechecks and service errors fail closed. No package names, private paths, URIs or raw service errors are displayed.

The caller requests cancellation after a 25-second polling deadline or a user cancellation/closed panel. Cancellation is best effort: one unfinished operation remains quarantined, with another check disabled until it reaches a terminal state. Late success cannot replace a cancelled or timed-out result. The operation is cancelled/released when the app is dropped. Synchronous WinRT activation/status/result calls are not a strict process deadline. Store results may be cached, and certification/public listing can lag; a successful query does not verify public Store availability, package trust for direct distribution or installation readiness. See the [native API and desktop window requirements](https://learn.microsoft.com/en-us/uwp/api/windows.services.store.storecontext.getappandoptionalstorepackageupdatesasync) and [owner-window interop](https://learn.microsoft.com/en-us/windows/apps/develop/ui/display-ui-objects). Native installed Store, window/service failure and cancellation acceptance remains pending.

This slice does not invoke Store install APIs, which can terminate the app; a future adapter must separate download/progress from installation and obey the restart gate. See [Microsoft's Store update API](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/package-updates-from-store).

Linux system installation paths and Flatpak context conservatively defer to the package manager. This does not claim a configured APT/Flatpak update repository. Direct distributions and local builds can check releases but have no direct installer configured. No channel competes with its Store or package manager.

## Shared restart protection

`workspace::lifecycle::update_readiness` is a read-only status check. A future verified native installer must recheck exact project/document/revision snapshots through `finish_update_exit`, alongside native UI gesture checks. This path rejects discard decisions, unsaved or externally conflicting sources, active file operations, loading and procedural code. It verifies the complete project set again and closes all projects atomically only after every check succeeds. A failed check leaves every project open. Ordinary human Save / Don't Save / Cancel close behavior is unchanged.

Save, PNG export, complete export batches, recovery checkpoints/discards and shared brush/tool/filter/export preference changes hold runtime activity counters through unlocked preparation and final writes. Counters are shared through engine clones or the workspace, remain outside PSD/history and prevent a previously clean readiness snapshot racing a newly started operation. Once atomic update exit closes the workspace, new guarded file and preference operations are refused. Shared preferences remain usable when a single original project tab closes normally. The native panel additionally reports unfinished strokes, transforms, parameter/text/selection gestures and file dialogs as blockers. There is no install/restart control wired to these APIs in this slice.
