# File safety (unreleased)

[Open-file ownership](file-ownership.md) prevents duplicate PSD/PSB opens across tabs, pending loads and PeerBrush processes. Content-based conflict checks remain independent: tests construct legacy document states without ownership and still verify that stale saves cannot replace newer artwork.

Save and PNG export capture the document identity and revision, the destination's file identity, timestamp, length and a streamed content fingerprint. The final replacement checks the captured source and destination again after flushing a same-directory temporary file. A changed source or destination rejects the operation, preserves current work and leaves the project open. Fingerprints detect accidental changes; they are not authentication hashes.

An instance that opened an older version cannot overwrite a newer save, including through equivalent paths. Use **Save As** with a new destination to retain both versions. Existing Save As and export destinations require explicit replacement consent: the native save dialog supplies it; MCP/CLI requests use `overwrite:true`. This consent never bypasses a loaded source conflict. Cooperative OS file locks serialize saves to the same destination across PeerBrush processes, independently of their instance-state directories.

Before replacing an existing PSD, PSB or PNG, PeerBrush flushes and verifies a byte-exact copy in `.peerbrush-versions` beside that file. This retains unsupported Photoshop structures and original precision. The three most recent preceding files per destination are retained after successful replacement. Storage is bounded to 1 GiB per directory; failure to preserve a prior version blocks overwriting. Save As to a new directory remains available. **File → Recover previous save** opens a selected PSD/PSB as a separate unsaved project with no original save destination. Inspect its contents and save under a new name. PNG versions remain ordinary image files. These private files and lock files belong outside source archives and Git.

New backup and replacement files copy existing Windows DACL access rules before receiving document bytes; Unix files preserve ownership, mode and platform ACLs. Inability to preserve access rules blocks replacement. Published file contents are read back and checked against the encoded bytes before a save can mark its project clean. Windows access-rule copying uses the documented [GetNamedSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getnamedsecurityinfow) and [SetNamedSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setnamedsecurityinfow) APIs. Cross-platform native verification must be reported separately.

Close and application exit review each dirty or conflicting project. A clean in-memory project whose saved file changed also requires a decision. Save As preserves both copies; **Don't Save** applies only to the reviewed in-memory source; **Cancel**, failed saves and changed sources keep projects open. Final exit validates the entire project set before closing anything.

Autosave checkpoints write separate recovery PSDs and immutable records. The original destination is metadata only; checkpointing and exit checkpointing never save into it. A checkpoint prepared from a revision that changed is deferred. The five-second interval, engine availability, 256 MiB encoded-file limit and recovery quotas still limit recoverability. A valid large document can exceed the save/checkpoint budget; see [the large-document investigation](large-document-investigation.md). A successful earlier checkpoint does not guarantee recovery of later edits. Recovery errors remain visible.

The reported duplicate-instance data-loss incident's original cause is unverified. Inspection of the published source found no automatic original-file save on exit. Confirmed weaknesses were size/timestamp-only file checks, missing final source-revision checks and absent independent destination guards for Save As/export. Verification must distinguish those fixes from reproduction of the original report.

Cooperative locks cannot stop another application from replacing a file immediately after the final check. Atomic replacement and verified prior files reduce that risk; they do not provide filesystem transactions across noncooperating applications, hardware durability guarantees or recovery from total disk failure. Keep independent backups. A crash before a complete checkpoint can lose subsequent unsaved edits. Previous-save cleanup runs only after successful publication; failed saves can leave additional verified versions until a later successful save, within the storage cap.

Verification: all 583 engine, codec, protocol and native UI regression checks passed, with eight opt-in checks ignored and one Windows clipboard-station check excluded. Coverage includes both close orders at 8/16-bit depth, restored timestamps, aliases, pending-source/destination changes, overwrite consent, quota/publication failures and cross-process locks released after a terminated process. Pointer-input tests verified Cancel, failed Save and Don't Save for a clean conflicting tab, and opening a dated previous version as an independent unsaved native-depth copy. Two isolated Windows app processes verified actual layered/masked native16 painting, stale-save rejection, visible close review, project closure and exact PNG16 reopening. Independent decoding matched the current standard merged composite and every unedited standard layer/mask/alpha word, hierarchy, bounds, clipping and blend. Private Windows DACLs and the byte-exact preceding PSD survived replacement. macOS/Linux permission code has not received native verification on this Windows host; cross-platform CI and native checks remain required before release. Failure injection tests exercise publication rejection and storage exhaustion, rather than claiming hardware power-loss simulation.
